# Limits and interpretation

- The decisive missing observation is the running kernel's `neigh_update` entry/return with the actual neighbor flags at the exact first-ARP processing instant, coupled to Zebra receipt and its decision to originate or withhold MAC/IP. The packaged VM lacks an available tracing tool and usable mounted tracefs; the Ubuntu build's exact kernel source and FRR binary-to-repository linkage were not verified. The upstream v6.8 code supports the hypothesis, not direct proof of the running binary. No software defect or standards violation is established.
- Five fresh trials per condition are small samples, in fixed order, with no meaningful seed variation for one robot. A successful pytest assertion means the harness ran, not that recovery happened. State snapshots are sequential and sparse; `None` means absent at the observation, not continuously absent. Actual movement times and worker offsets vary; offsets are measured from worker start after attachment and snapshot commands, not exact link transition. Monitor notifications report userspace receipt, not precise kernel transition times.
- The `none` condition has no deliberate worker frames, but priming, neighbor aging, controller ICMP, gateway replies, and spontaneous robot ARP continue. ARP-analysis rows classify unmatched frames as background **or unmatched**: a reply to a worker ARP may be in that group, and timestamp matching is a candidate, not a unique ARP identifier. The delayed-01 route recovered before its scheduled request. These confound attribution to any single deliberate ARP.
- `dumpcap` reported zero receive/drop, pcap, dumpcap, flushed and interface drops for all 232 capture logs. This does not establish that a packet crossed every interface, that all packets were captured before capture startup, or that the protocol dissector/reassembly is perfect. The 20 matched Leaf2 neighbor listeners recorded no socket error but did not record an end-of-run `/proc/net/netlink` drop count. The extra access-port validation did record start/end socket rows with zero drops. That extra run waited 200 ms before worker startup and is not statistically comparable with the main trials.
- PCAP times and `ip -ts monitor` use realtime; listener records userspace realtime and monotonic after receive; snapshot commands and probes use monotonic. Per-worker bracketing provides local paired clock observations but no calibrated bound on scheduling, PCAP timing, monitor delivery or clock steps. Do not calculate exact cross-domain latencies or infer an exact outage from 10 Hz probes. Socket receive timestamps were not supplied in ancillary data. Netlink `FAILED` and `DEL` observations alone do not establish the process that issued a delete.
- `any` captures can duplicate packets. BGP UPDATE decodes are per capture and peer, potentially including reassembly/retransmission artifacts; no raw count is a count of unique changes. IP neighbor and MAC/FDB are distinct. Packet paths identify frames and tunnel headers; the exact location of seq60's failure remains unknown even with zero reported capture drops. No controller application location state was measured.
- Only BBM on this Linux emulator was tested. No topology scaling or DAD sweep, AP-model run, or targeted MBB comparison was made. Results cannot be extrapolated to a production switch, a different kernel, or a fleet. The teammate's AP trace was unavailable. No core source or production configuration was edited.

# Kernel and FRR source analysis

The running environment reports Linux `6.8.0-117-generic` aarch64 and FRR `10.8.0-dev-my-manual-build`; exact Ubuntu kernel build source and the FRR binary-to-checkout correspondence were not established. The following is a source-level analysis of **upstream Linux v6.8**, not direct proof that the vendor binary executed identical instructions. See [upstream ARP processing](https://github.com/torvalds/linux/blob/v6.8/net/ipv4/arp.c), [neighbor processing](https://github.com/torvalds/linux/blob/v6.8/net/core/neighbour.c), and [kernel IP sysctl documentation](https://www.kernel.org/doc/html/v6.9/networking/ip-sysctl.html).

- For an ARP request addressed to a local IP, `arp_process` can call `neigh_event_ns` for the sender and send a reply. In upstream v6.8, `neigh_event_ns` calls `neigh_update` with `NUD_STALE` and `NEIGH_UPDATE_F_OVERRIDE`, without `NEIGH_UPDATE_F_ADMIN`. `__neigh_update` returns early for an existing `NUD_NOARP` or `NUD_PERMANENT` entry when the update is nonadministrative. `OVERRIDE` and `ADMIN` have different semantics. Thus an ARP reply being emitted does not itself prove the neighbor was locally learned. This is an explicit kernel behavior for the v6.8 source path, contingent on reaching that path and on the actual kernel build.
- Upstream `neigh_update_flags` changes `NTF_EXT_LEARNED` for administrative updates; an external entry is also exempt from ordinary periodic garbage collection. Exemption from garbage collection is not a guarantee against an explicit deletion or all other state transitions. `arp_accept` controls creation from unsolicited/gratuitous ARP when no entry exists; it does not mean every ARP request to a local gateway is discarded. The experiment records `arp_accept`, `arp_ignore`, `arp_filter` and `arp_announce` in each leaf2 `arp_policy` event; no sysctl was modified.
- In the checked-out FRR code, `zebra/zebra_evpn_neigh.c:97–115` installs a remote neighbor with externally learned flags. At `:880–925`, local-MAC changes process local neighbors and deliberately do not unconditionally uninstall associated remote neighbors, because that could race with a newly learned local neighbor. The comment's TBD is not a defect finding. `zebra/zebra_vxlan.c:4403–4451` classifies kernel neighbor updates; `zebra/zebra_evpn_neigh.c:1216–1550` handles a separate local neighbor update and can send eligible MAC/IP to BGP. Local MAC learning is not sufficient by itself to establish local IP. `zebra/zebra_evpn_mac.c:2267–2310` updates MAC ownership and mobility sequence.
- An old MAC/IP route withdrawal can trigger removal of the remote neighbor; `zebra/zebra_evpn_neigh.c:800–816` calls dataplane neighbor deletion. `zebra/rt_netlink.c:4870–4925` encodes neighbor operations; upstream Linux `neigh_delete` uses an administrative update to `FAILED` and removes the neighbor. Correlated notification state and BGP messages are consistent with this path but do not prove the sender or invocation without a tracepoint or netlink request capture. The observed timing of a later request after removal can therefore differ materially from a request while the old entry remains.

The result may reflect an interaction among application announcement timing, Linux neighbor policy, and FRR's safety choice. It could be configuration- or implementation-specific. Neither the normal upstream kernel guard nor FRR's conservative comment alone establishes a standards violation, a production defect, or a fix.

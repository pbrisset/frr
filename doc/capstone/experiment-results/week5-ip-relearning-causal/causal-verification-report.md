# Causal verification report

**Decision: CAUSAL MECHANISM PARTIALLY SUPPORTED.** The controlled evidence and upstream kernel code are consistent with an early ARP arriving while a remote `NOARP` neighbor prevents ordinary local relearning, followed by old-route withdrawal, deletion and a later local-neighbor event. The internal kernel function invocation/return and Zebra notification processing were not traced, and the exact Ubuntu kernel source corresponding to the running binary was not verified. The sequence is not established as the sole cause or as an FRR defect. See `hypothesis-status.csv` for each step's separate status and counterevidence.

## Controlled comparisons

Twenty fresh topologies, five per condition, used the same single-veth Leaf1→Leaf2 BBM harness and observation window. All completed the test's basic checks; success of a test invocation is not evidence of convergence. The 21st access-port run added 200 ms of capture-start wait and is excluded from the matrix. DAD was held at baseline enabled, 5 moves/180 s, confirmed in each leaf's recorded `show evpn`. Controller ICMP probes were requested at 10 Hz; per-run realized send rates are in `intervention-trials.csv`. Seed 1–5 changes a one-element shuffle and creates no meaningful randomized schedule; fresh topologies provide separate executions, not randomized population samples. Conditions were run in a fixed repeated order.

| Condition, n=5 | Controller probe losses per run | Sampled Leaf2 local IP and Leaf5 /32 via Leaf2 | Qualification |
|---|---|---|---|
| No deliberate post-move ARP | 68, 69, 1, 76, 70 | 1/5 | Naturally emitted ARP and controller traffic still occur. Four runs ended with no observed recovery. |
| One immediate gateway ARP request | 67, 70, 1, 75, 70 | 1/5 | One early request is not equivalent to a successful local-neighbor update; four runs ended without observed recovery. |
| One gateway ARP request after 3 s | 1, 18, 19, 19, 18 | 5/5 | In delayed-01 the /32 was restored **before** the scheduled request, so that intervention cannot be credited. Other traffic is not suppressed. |
| Four gateway ARP requests, nominal worker offsets 0/250/500/750 ms | 0, 1, 0, 1, 1 | 5/5 | Actual sends are timestamped; natural ARP and other traffic remain possible causes. |

All 30 scheduled worker requests in the matched matrix have timestamp-matched candidate frames at both host11 and the Leaf2 bridge; the extra direct-port run also captured its one scheduled request at the access port. These matches do not by themselves establish kernel processing. Each sampled local-IP case also has a decoded Leaf2 sent MAC/IP NLRI, and a later sampled Leaf5 /32 via Leaf2. Counts of BGP transmissions include both peers and capture artifacts, not unique changes. Probe loss is a timeout/error observation, not an exact outage. Failure runs with no reply before observation ended are right-censored. The rates are descriptive of this emulator and instrumentation, not estimates of fleet or production reliability. `intervention-trials.csv` includes all sends, replies, loss, observed recovery and failed interventions; `leaf5-forwarding-transitions.csv` contains samples and route monitor events.

## First-ARP evidence

In `raw-immediate-01`, Leaf2's pre-stimulus snapshot recorded the robot neighbor as externally learned, `NOARP`, protocol Zebra; its Zebra neighbor was remote. The worker sent a gateway ARP at realtime 1793765292.408122; Leaf2 bridge PCAP frame 1 observed the robot request at 1793765292.408138 and frame 2 shows a gateway reply. The Leaf2 netlink listener later received `RTM_NEWNEIGH` state 0x20 (`FAILED`) at 1793765292.439302 and `RTM_DELNEIGH` at 1793765292.439539, with no earlier robot neighbor update recorded by that listener. Subsequent snapshots show the Leaf2 MAC local and the IP neighbor absent; Leaf5 netlink shows /32 deletion. The capture reported zero drops. These observations are consistent with the entry remaining at ARP time, but the prior kernel snapshot is not atomic with the ARP, the monitor records userspace receipt, and that run has no final socket-drop counter. The exact kernel neighbor update call and return are UNKNOWN.

In separate `raw-access-01`, the direct Leaf2 access-port capture recorded a natural robot gateway ARP request in `leaf2-port.pcapng` frame 2 at 1793766145.063754, followed by the listener's failed/deleted neighbor events at 1793766145.085116–.085354. A pre-move snapshot showed the external `NOARP` entry, and the checked listener's `/proc/net/netlink` row reported zero drops at start and end. The direct-port capture also reports zero drops. A 200 ms instrumentation wait changed this run's timing, and the listener still supplies receive times rather than the kernel function time; it does not prove the exact state during the ARP.

## Recovery sequence and counterexample

In `raw-delayed-02`, the old external neighbor was recorded failed/deleted at realtime 1793765569.370674–.370781. The worker's 3-second gateway ARP send began at 1793765572.334251; the Leaf2 listener recorded a local `STALE` neighbor at 1793765572.334373, Leaf2 capture decoded MAC/IP Type-2 announcements at 1793765572.385805 and .385855, and Leaf5 monitor recorded /32 via Leaf2 at 1793765572.500388. Controller replies recovered. The observations fit the proposed chain, but do not trace Zebra's internal processing or exclude every incidental trigger. In `raw-delayed-01`, Leaf5's /32 returned at 04:10:02.968802 while the scheduled worker send was at 04:10:05.787441; this is explicit counterevidence against crediting every delayed intervention.

For a failed probe and a successful different-leaf fallback, see `controller-packet-paths.csv`. Immediate-01 ICMP id 42000 seq 60 reached Leaf3 but no matching packet or reply was observed at the robot/controller. All relevant capture logs report zero drops, yet the exact loss or queue location is UNKNOWN. Repeated-01 seq 44 followed Leaf5→Leaf3 over VNI500, Leaf3→Leaf2 over VNI1000, reached the robot and returned to the controller. A wrong first VTEP can deliver; a /24 fallback does not itself prove loss.

## Engineering interpretation

The current evidence justifies targeted testing of the kernel-neighbor/Zebra boundary, not a core patch. The lowest-cost remaining BBM test is a small number of instrumented paired early-versus-post-withdrawal ARPs with direct `neigh_update` entry/return and Zebra event or netlink-request tracing, verified clock calibration and per-socket loss counters. Demonstrating that the early ARP invokes the running kernel's update with an existing `NUD_NOARP` entry and that the nonadministrative call rejects it, while a controlled later request leads to a Zebra local-neighbor notification and advertisement, would close the main internal-observation gap. An observed successful local update despite that precondition, or absence of the guard in the exact vendor kernel, would falsify the proposed necessary mechanism. More uninstrumented BBM repeats add little. Defer claims about MBB and fleet until targeted comparable tests and the teammate's AP harness are available; a limited MBB comparison can proceed in parallel only if the research priority requires it and its differing semantics remain separate.

Scope: retrospective analysis of recorded Phase 0 and Phase 1 evidence. No trial is re-executed. Matrix manifest revision is `709ca316646823ef1ad64f05e4e60174db0c2199`; the experiment harness was untracked when captured, so the commit alone is not full source provenance. ## Phase 1A — MBB Implementation Validation

**Verified implementation and smoke evidence.** The source `source/tests/topotests/bgp_evpn_capstone/test_phase1_mbb.py` creates a veth pair inside the existing host11 namespace, assigns the new host-side interface `mbb-host` the same MAC as `eth0`, moves its peer into leaf2 and connects it to `br1000`. In `phase1/smoke-03/events.json`, the `overlap_snapshot.host` command output lists both `eth0` and `mbb-host` with `00:00:00:00:00:11`, and only `eth0` with the robot IPv4 address `45.0.0.11/24`. Each interface also has a Linux link-local IPv6 address; the single-IP assertion concerns the robot's specified IPv4 identity. The test explicitly asserts that the robot IPv4 address occurs once and that both leaf access ports are attached before removal. These are one namespace and one configured robot IPv4 identity, not two independent hosts.

`source/tests/topotests/bgp_evpn_capstone/phase1/announce.py` sends an Ethernet broadcast gratuitous ARP request using the robot MAC and IPv4 as sender through `mbb-host`. In smoke-03 the `gratuitous_arp_sent` command-completion event is at monotonic 25692284514540 ns; the sequential overlap snapshot reports leaf2 Zebra MAC `00:00:00:00:00:11` as `local` on `mbb-leaf`, `localSequence=1`, `detectionCount=1`, `isDuplicate=false`. The same snapshot records leaf1 as local, sequence 0, but its leaf snapshots are sequential and do not establish an atomic simultaneous control-plane view. The new attachment event is at 25692266123034 ns and `old_detached` at 25692528387584 ns, with reported command-observation overlap 262.265 ms for a requested 250 ms. These are userspace observations, not exact kernel transition times.

**Receive and reply during overlap: not established.** The test sends ARP through the new interface but does not send and trace a controller-originated packet through leaf2 during overlap. `mbb-host` has no robot IPv4 address in the overlap snapshot; host routing and Linux weak-host behavior could allow some inbound traffic to be accepted on an interface other than the one owning the address, but the evidence does not prove receipt or a response through the new link. The default route remains configured via `eth0` during overlap. The code detaches leaf1 first, then deletes the robot IPv4 address from `eth0`, adds it to `mbb-host`, and replaces the default route. These separate commands are not atomic; smoke-03 does not timestamp their individual completions. The `controller_reachable` event follows the transfer and a successful ping check; it proves a post-transfer reply was observed, not continuous connectivity or overlap-time new-interface reachability.

**Repeated learning and scope.** Phase 1B's sampled leaf2 local sequence and DAD detection count reached 3 in three MBB-250 and five MBB-500 matrix runs. Repeated source-MAC learning on the two still-attached paths could explain this, including possible traffic on the old interface after the gratuitous ARP. That is a hypothesis: the samples do not trace every ingress frame or establish the precise sequence of relearns. No sampled duplicate flag was true. The implementation establishes a real overlap of two physical virtual access attachments, followed by a single-IP/route transfer; its stimulus demonstrates new-leaf MAC learning. It does not demonstrate simultaneous usable IP paths, uninterrupted connectivity, radio association, or a complete production wireless make-before-break handoff. See the Phase 1A implementation report `phase1/README.md`, source and `phase1/smoke-03/events.json`; the available smoke directories contain event JSON only, with no retained Phase 1A packet capture or standalone pytest log. The original report records 1 passed in 28.28 seconds, and the failed first attempt remains in `phase1/attempt-01/events.json`.

## A. Environment and topology

Two spines (AS65000) connect to all five leaves (AS65011–65015) using eBGP unnumbered and EVPN address families. Eight configured robot hosts attach to leaves1–4; the controller `20.0.0.51` attaches to leaf5. Only host11 (`45.0.0.11`, MAC `00:00:00:00:00:11`) moves leaf1 → leaf2. Robot L2VNI is 1000, L3VNI is 500, and tenant routing uses VRF500. Leaves1–4 advertise subnet reachability; leaf5 imports remote host routes and forwards through the L3VNI, resolving a route gateway through a neighbor RMAC and the VNI500 FDB to a VTEP. The `/32` normally beats the robot `/24`; a present `/24` by itself does not prove actual fallback. The fabric, not the controller application, learns attachment through EVPN; this is not a physical-position API.

The recorded environment is a privileged Ubuntu 22.04.5 Linux aarch64 container under Colima, kernel 6.8.0-117-generic and FRRouting 10.8.0-dev-my-manual-build. Raw environment commands, CPU/cgroup state, FRR configuration, DAD setting and version are in each run's `events.jsonl`; `manifest.json` gives parameters, clock namespace and commit. The route/FDB/link snapshots are kernel state; `show evpn` is Zebra; EVPN RIB and neighbor commands query bgpd; tshark PCAP decoding observes wire messages; a separate controller raw-ICMP process supplies send/reply and timeout observations. None is an exact internal Zebra/bgpd transition timestamp.

## B. Mobility implementation

The exact recorded-path implementation is in `source/tests/topotests/bgp_evpn_capstone/test_phase1_comparison.py`; Phase 1A test and `announce.py` are included. BBM detaches `eth-host11` from leaf1 bridge, transfers the same veth into leaf2, attaches it to `br1000`, and sends gateway pings. The calculated disconnected interval spans command observations, not the exact kernel transitions. In MBB, host11 remains one namespace: it creates a second veth, sets host-side `mbb-host` to the same MAC, moves its peer `mbb-leaf` into leaf2, and attaches it to `br1000` while leaf1 remains connected. The existing IP and route remain on eth0; the new interface has no separate IP assignment. A raw Ethernet gratuitous ARP request with host11's sender MAC/IP is sent through the new interface, and a Zebra query confirms local learning at leaf2. After at least the requested wait, the old port is detached; the single IP and default route are moved to `mbb-host` and host11 pings the gateway. Cleanup removes the temporary veth, restores address/default route and reattaches leaf1. Both host-side interfaces are not bridged together. Linux weak-host receive behavior remains unmeasured.

Physical dual attachment is not concurrent normal IP routing: configured egress remains on eth0 during overlap and transfers only after old-port removal. The additional Zebra query can extend overlap. No actual radio, AP association, wireless roaming protocol or production robot is modeled; the ARP-triggered dual-attachment emulator is not a complete wireless handoff. Duplicate MAC activity is not suppressed. MBB-250's Phase 1A smoke and two pilots are separate from the matrix.

## D. Control-plane lifecycle

Before each move, sampled Zebra showed leaf1 local and leaf2 remote. BBM detachment removes the old access binding and the new leaf learns after reattachment/traffic. In MBB, leaf2 confirms local MAC learning while old physical attachment remains; the overlap query captures the new leaf's state, but does not provide an atomic simultaneous two-leaf view. Kernel FDB events go through Zebra to bgpd according to the Phase 0 source audit; those internal transitions are not directly timed in these runs.

The initial leaf2 local sequence/detection count reached 1/1 in every run. Three MBB-250 and five MBB-500 runs reached a sampled leaf2 local 3/3, indicating additional observed mobility-related state changes; the exact cause and precise number/timing of physical or logical relearns cannot be established by these snapshots alone. No robot duplicate flag was true in the collected samples; that is not a continuous DAD monitor.

Phase 1A's `smoke-03/events.json` records leaf1 local MAC-only and MAC/IP routes in its overlap snapshot, and leaf2 local MAC-only under its RD with old leaf1 routes still visible; later, leaf2's RD has MAC-only and MAC/IP entries. In the matrix, device RIB snapshots and wire NLRI records distinguish MAC-only `ipLen=0` and MAC/IP `ipLen=32`; two spine peers generate separate paths and copies. `raw/<trial>/packet-events.jsonl` retains per-message decoded NLRIs for leaf1, leaf2, both spines and leaf5; `bgp-robot-nlri.csv` indexes robot NLRIs, and `bgp-messages.csv` gives per-device message counters. These observations support propagation through the captured spine adjacencies, not exact enqueue or per-route installation timing. For example BBM-1 leaf1 sent a captured robot withdrawal before leaf2 sent its MAC-only advertisement; MBB100-1 shows leaf2's announcement before the captured old-leaf withdrawal on the realtime capture clock. Multiple transmissions, capture-window boundaries and reassembly constrain interpretation. They cannot be aligned exactly with monotonic attach/detach events.

On leaf5, imported EVPN state is sampled in BGP JSON; the kernel host route, broader subnet, route-get, neighbor and FDB are separately queried. Consequently one cannot infer exactly when bgpd selected a path, when Zebra programmed it, or how long any intermediate state lasted. Sampled BGP neighbors were Established throughout, but short resets between samples are not excluded.

## E. Forwarding and reachability

The sampled host `/32` was absent in 4/5 MBB-100 and 5/5 MBB-500 runs; none was sampled absent in the matrix BBM or MBB-250 groups. Each of those nine runs also had a leaf5 resolution sample pointing to leaf3 (`10.0.0.3`) while tracked attachment was leaf2. The `/24` ECMP route retained four leaf nexthops. A `/24` fallback selecting leaf3 is a plausible reading of the route and lookup observations, as in the Phase 0 example, but separate sequential route-get, neighbor, FDB and table reads cannot prove an atomic state or which route an individual probe used. The ECMP selection inputs and concurrent transitions are not isolated, so why leaf3 was chosen is unproven.

Mismatch without a probe loss is unsurprising as a measurement possibility: 10 Hz probes can miss a brief condition, and a delayed/retried or differently timed packet may succeed. This is not proof of any of those mechanisms. The raw `any` captures are provided for follow-up; no packet-level correlation in the existing analysis establishes the drop location or ties a lost packet to the IP/default-route transfer. Probe timeouts and the approximate 1-second response tail are not exact network outage lengths.

## F. Comparison

The 20 losses per group are BBM 0,0,0,1,1; MBB-100 0,0,0,0,0; MBB-250 0,0,0,1,0; MBB-500 0,1,1,0,3. Median losses are 0,0,0,1 respectively. The longest observed loss burst was 3 in MBB-500-5. `comparison.csv` provides min/median/max and `runs.csv` per-run RTT distributions and observed interval; the full per-probe distribution is in `reachability.csv`. More churn in selected MBB runs and a larger observed mismatch count do not establish statistical significance, a causal relationship, or production performance. A single fixed method order may confound environment/time effects. The original pilots were 0 losses for BBM and 1 for MBB-250; they are not included in the matrix aggregates.

## G. Instrumentation limits

Sampling is slow, sequential and non-atomic; exact `/32` disappearance, stale duration and intervening state are unknown. Packet capture uses realtime and event/probe clocks use monotonic without a calibrated offset or error bound; no exact cross-clock order is justified. There is no route/FDB/neighbor netlink event stream. Controller ICMP is one flow, with approximately 10 Hz realized sampling and one-second timeout, not all application traffic or an exact outage timer. PCAP `any` can duplicate traffic and capture loss was not comprehensively certified. BGP message totals are per observation point and transmission; withdrawal NLRI counts are not unique announcements. The MBB-only verification and snapshot workload, variable VM scheduling, shared resources, uncapped Docker allocation and fixed trial order can affect timing. Results are emulated, not hardware or wireless production performance.

## H. Prioritized open engineering questions

1. **What happened to controller packets during missing `/32` states?** Observation: nine MBB runs sampled /32 absence and a leaf3 resolution, while losses varied. Hypotheses: an ECMP fallback misdirected some packets; the condition occurred between probes; delayed delivery or a different transition explains the observations. Evidence: time-aligned packet identifiers at controller, leaf5 encapsulation and leaf1–4 decapsulation, with capture-loss accounting. Next: synchronized access/VXLAN capture plus a calibrated monotonic/realtime mapping and netlink subscription.
2. **Why do longer overlaps show sequence 3 and additional Type-2 churn?** Observation: eight MBB-250/500 trials sampled leaf2 seq 3. Hypotheses: old-interface traffic after the new ARP triggers alternating MAC ownership; ARP/neighbor events or another source-learning stimulus contribute. Evidence: timestamped source-MAC ingress on both access ports paired with BGP/Zebra/netlink events. Next: capture per-port frames and compare controlled old-egress suppression versus ordinary traffic, without changing FRR.
3. **How does `/32` withdrawal and reinstallation relate to MAC-only and MAC/IP route lifecycle?** Observation: some route snapshots lack /32 while the /24 remains; separate BGP packet records include announcements and withdrawals. Hypotheses: MAC/IP withdrawal and relearning drive the temporary gap, or another ordering/selection effect contributes. Evidence: synchronized per-message NLRIs, Zebra neighbor events and kernel route transitions. Next: netlink and clock-calibrated captures; retain a baseline workload and avoid claiming internal timing from CLI snapshots.
4. **Does moving the IP/default route contribute to interruption?** Observation: MBB moves these after physical detach and several runs lost probes. Hypotheses: host route/address transition, control-plane reconvergence, or probe scheduling; current evidence does not distinguish them. Evidence: per-command entry/exit, host link/address/route netlink and packet traces. Next: compare a separately justified alternative host identity model with matched background workload and appropriate controls.
5. **Are results robust to schedule and observer load?** Observation: five runs per setting ran in a fixed order, with extra MBB observation. Hypotheses: method effect, time/resource drift, or instrumentation overhead. Evidence: randomized paired run order, VM CPU pressure and capture loss. Next: randomize and repeat only after measurement validation, with stable workload and documented allocation.

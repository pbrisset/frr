# Protocol and forwarding walkthrough

The topology is a virtual Linux/FRR fabric: leaf1–4 are VTEPs for robot L2VNI 1000 (`45.0.0.0/24`); leaf5 attaches the controller `20.0.0.51/24`; the tenant routed overlay is VRF/L3VNI 500. Each leaf peers with both spines over eBGP unnumbered and exchanges EVPN. See `tests/topotests/bgp_evpn_capstone/test_evpn_capstone.py` and the checked-in leaf/spine configurations. The exact teammate AP model is unavailable and cannot be inferred from this topology.

1. **Attachment and identity.** BBM in Phase 0/1 transfers the same access-side veth from old bridge to new bridge; it is physically disconnected over an observed command interval. MBB creates a second same-MAC veth and sends a raw gratuitous ARP while the original link, IPv4 and default route remain present; only after old detach does the single IP/route transfer. Separate command completion observations bound attachment; they do not timestamp kernel transitions. In neither case is a real radio association modeled.
2. **Kernel learning.** Incoming source frames can update the bridge MAC/FDB. The IPv4 neighbor table is distinct. Before a BBM move the new leaf may contain a Zebra-installed remote robot neighbor flagged externally learned and `NOARP`. A frame captured on a bridge or port does not alone prove how the kernel processed it. The causal access run observed a robot ARP, followed by a failed/deleted neighbor notification; its exact in-kernel state at ARP processing remains unknown.
3. **Zebra.** Zebra maintains local/remote EVPN MAC and neighbor state separately. A remote MAC learned locally obtains a mobility sequence, while neighbor handling requires a separate local-neighbor event. Code deliberately avoids blindly deleting a remote neighbor on local MAC change because of a possible race with a new local neighbor. The local-MAC sample alone does not prove local IP learning or a defect.
4. **bgpd and spines.** Zebra informs bgpd of eligible local MAC-only and MAC/IP Type-2 routes; old local ownership can be withdrawn and new announcements sent to both peers. Spines distribute them to other leaves. PCAPs include actual messages and robot NLRI decodes; messages can carry multiple announcements/withdrawals, and capture direction, TCP retransmission and two peers matter. Device-capture totals are not fabric-wide unique route changes.
5. **Remote selection and installation.** Remote bgpd selects paths and communicates relevant state to Zebra. Zebra and Linux program FDB, neighbor and VRF routes. Available snapshots do not timestamp each internal decision and are not atomic. In Phase 0, Leaf5's old host route disappeared in a sample while Type-5 /24 ECMP remained, and later a robot /32 via leaf2 was sampled. The causal trial's route monitor captures deletion and, in recovery cases, reinstallation.
6. **Leaf5 and packets.** Longest-prefix matching normally favors the robot /32 when installed. Without it, the broader /24 may select another leaf; route-get, neighbor/RMAC and VXLAN FDB form an inferred routed VTEP chain. The controller application was not queried, so forwarding state is not application location knowledge. One failed ICMP request reached leaf3 with no observed reply; its drop is unlocated. A separate ID 42000 seq 44 capture follows leaf5→leaf3 (VNI500)→leaf2 (VNI1000)→robot, then the reply returns. Wrong first VTEP can still deliver.
7. **Recovery.** In one delayed gateway-ARP trial, the old neighbor was observed deleted, a later robot request was captured, Leaf2 recorded a local `STALE` neighbor, bgpd emitted MAC/IP Type-2 and Leaf5 installed a /32 through leaf2. Another trial restored the /32 before its scheduled request. Upstream Linux v6.8 has a nonadministrative `NOARP` update guard, but the exact running-kernel invocation and Zebra decision were not traced; this causal mechanism remains partially supported.

Monotonic command and probe events are separated from PCAP realtime. The causal monitor records userspace wall/monotonic receive times and paired worker clocks but has no rigorous bound on scheduling or kernel-event delivery. Even zero reported capture drops does not establish a precise drop point or atomic state. Consult `week5-ip-relearning-causal/causal-verification-report.md`, `hypothesis-status.csv` and raw PCAPs for the exact evidence and alternatives.
